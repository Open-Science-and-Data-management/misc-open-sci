ผังข้อมูล maDMP

อ่านสเปก 318 KB ให้เหลือภาพเดียว — ทุกอย่างห้อยอยู่กับ "แฟ้ม" เดียวที่ชื่อ dmp และทุกกล่องถูกออกแบบมาให้ เครื่องอ่านได้ ไม่ใช่แค่คน

ผังความสัมพันธ์ของข้อมูล (ER Diagram)

วาดจากตาราง properties และค่า cardinality ใน README จริง — เรียงจากบนลงล่างตามชั้นของข้อมูล

ชี้เมาส์ (หรือแตะ) ที่กล่องบนผัง → ความเห็นของคนออกแบบฐานข้อมูลเรื่องตารางนั้น ๆ

  • • = ช่อง required (บังคับกรอก)
  • 1 = ต้องมี 1 อัน
  • 0..n = ไม่มีก็ได้ / มีกี่อันก็ได้
  • 0..1 = ไม่มีก็ได้ แต่มีได้แค่อันเดียว

มันทำงานยังไง — ไล่ตามผังทีละชั้น

ลองนึกว่ามันคือ "แฟ้มโครงการวิจัย 1 เล่ม" ที่อยู่ในรูปแบบที่คอมพิวเตอร์อ่านออก

  1. เริ่มที่แฟ้มปก: dmp

    ทุกอย่างอยู่ใน dmp แฟ้มเดียว — ชื่อแผน, ภาษา, วันที่สร้าง/แก้ไข, ตัวตนของแฟ้ม (dmp_id), มีปัญหาจริยธรรมไหม และสถานะอนุมัติ (approval) แถมมาติดกับปกเลย

  2. ชั้นคน: contact กับ contributor

    แฟ้ม 1 เล่ม มี ผู้ติดต่อ 1 คนเท่านั้น (cardinality = 1) แต่มีทีมงาน (contributor) กี่คนก็ได้ ทุกคนมี "ID อ้างอิง" ของตัวเอง เช่น ORCID และสังกัด (affiliation) ได้หลายที่

  3. ชั้นข้อมูล: dataset → distribution

    ตรงนี้คือหัวใจ — dataset คือ "ข้อมูลในความคิด" ยังไม่ใช่ไฟล์ (ต้องมีอย่างน้อย 1 ชุด) ส่วน distribution คือ ไฟล์จริงที่เอาออกแจก — ข้อมูล 1 ชุด แจกได้หลายรูปแบบ (CSV หนึ่งอัน, JSON หนึ่งอัน, เวอร์ชันไม่ระบุตัวตนอีกอัน) แต่ละไฟล์มี license กับ host (ตู้เซฟที่เก็บ) ของตัวเอง

  4. ชั้นโครงการและเงิน: project → funding / partner_organization

    แฟ้มผูกกับโครงการได้หลายโครงการ แต่ละโครงการมีแหล่งทุนกับหน่วยงานร่วมงานเป็นของตัวเอง พร้อมสัญญาร่วมงาน (agreement — MOU, สัญญาแบ่งเงิน ฯลฯ) แนบไว้

จำง่าย ๆ ด้วยตารางนี้

ศัพท์ในผังเทียบกับแฟ้มโครงการกฎความสัมพันธ์
dmpตัวแฟ้ม 1 เล่มแกนกลาง — ทุกกล่องห้อยอยู่ใต้มัน
contact · contributorเบอร์ติดต่อ · ทีมทำงานติดต่อได้ 1 คน (บังคับ) · ทีมกี่คนก็ได้

project · fundingโครงการ · แหล่งเงินทุนผูกกับแฟ้มได้หลายรายการ

3 กฎที่ทำให้ "เครื่องอ่านได้"

บังคับน้อย แต่บังคับชัด

เริ่มต้นมีแค่ 13 คำถามที่ต้องตอบ (ชื่อผู้ติดต่อ, ชื่อ dataset, มีข้อมูลส่วนบุคคลไหม ฯลฯ) ที่เหลือเป็น optional — แล้วค่อยบังคับเพิ่มตามที่โครงการเดินไปถึงช่วงไหนของชีวิตข้อมูล

คำตอบต้องเลือกจากลิสต์

หลายช่องเป็น controlled vocabulary — เช่น การเข้าถึงตอบได้แค่ open / shared / closed เครื่องเลยไม่มีทางตีความคำตอบผิด

ID ใช้แม่แบบเดียวกันทั้งเล่ม

dmp_id, dataset_id, contact_id… ทุกตัวเป็นกล่องสำเร็จรูปเหมือนกัน: identifier + type + registry_name — เขียนโค้ดอ่านครั้งเดียว ใช้ได้กับทุกช่อง

ตารางอ้างอิงฟิลด์ราย entity

สรุปจากตาราง Properties ใน README โดยตรง — คำอธิบาย, เงื่อนไขบังคับ, cardinality, ตัวอย่าง และคำถามฉบับผู้ใช้ (เลื่อนตารางได้ในแนวนอน)

ควรมีตารางนี้ไหม: มีก็ดี — แต่ข้อมูลอย่าง "สำรองทุกวัน" เก่าเร็ว ให้ถือระบบจริงเป็นตัวตั้ง แล้วมองข้อมูลตรงนี้เป็นภาพ snapshot ณ ตอนเขียนแผน
