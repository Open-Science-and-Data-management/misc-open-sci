ผังข้อมูล RDA maDMP

อ่านสเปกทั้งเล่มให้เหลือภาพเดียว — ทุกอย่างห้อยอยู่กับ "แฟ้ม" เดียวที่ชื่อ dmp และทุกกล่องถูกออกแบบมาให้ เครื่องอ่านได้ ไม่ใช่แค่คน

ผังความสัมพันธ์ของข้อมูล (ER Diagram)

วาดจากตาราง properties และค่า cardinality ใน README จริง — เรียงจากบนลงล่างตามชั้นของข้อมูล

ชี้เมาส์ (หรือแตะ) ที่กล่องบนผัง → ความเห็นของคนออกแบบฐานข้อมูลเรื่องตารางนั้น ๆ

  • • = ช่อง required (บังคับกรอก)
  • 1 = ต้องมี 1 อัน
  • 1..n = ต้องมีอย่างน้อย 1 อัน
  • 0..n = ไม่มีก็ได้ / มีกี่อันก็ได้
  • 0..1 = ไม่มีก็ได้ แต่มีได้แค่อันเดียว

มันทำงานยังไง — ไล่ตามผังทีละชั้น

ลองนึกว่ามันคือ "แฟ้มโครงการวิจัย 1 เล่ม" ที่อยู่ในรูปแบบที่คอมพิวเตอร์อ่านออก

  1. เริ่มที่แฟ้มปก: dmp

    ทุกอย่างอยู่ใน dmp แฟ้มเดียว — ชื่อแผน, ภาษา, วันที่สร้าง (created — ห้ามแก้หลังสร้าง) วันที่แก้ล่าสุด (modified — ตัวบอกเวอร์ชัน), ตัวตนของแฟ้ม (dmp_id) และมีปัญหาจริยธรรมไหม (ethical_issues_exist)

  2. ชั้นคน: contact กับ contributor

    แฟ้ม 1 เล่ม มี ผู้ติดต่อ 1 คนเท่านั้น (cardinality = 1) แต่มีทีมงาน (contributor) กี่คนก็ได้ ทุกคนมี "ID อ้างอิง" ของตัวเอง เช่น ORCID และสังกัด (affiliation) ได้หลายที่

  3. ชั้นข้อมูล: dataset → distribution

    ตรงนี้คือหัวใจ — dataset คือ "ข้อมูลในความคิด" ยังไม่ใช่ไฟล์ (ต้องมีอย่างน้อย 1 ชุด) ส่วน distribution คือ ไฟล์จริงที่เอาออกแจก — ข้อมูล 1 ชุด แจกได้หลายรูปแบบ (CSV หนึ่งอัน, TIFF หนึ่งอัน) แต่ละไฟล์มี license กับ host (ตู้เซฟที่เก็บ) ของตัวเอง ข้อมูลชุดเดียวกัน "แจกได้" แม้แผนจะยังไม่เคยถูกทำจริงเลย

  4. ชั้นโครงการและเงิน: project → funding / cost

    แฟ้มผูกกับโครงการได้หลายโครงการ (ไม่ใช่แค่โครงการที่ได้ทุน — โครงการภายใน, วิทยานิพนธ์ ก็ได้) แต่ละโครงการมีแหล่งทุน (funder_id อ้างทะเบียนกลาง) เป็นของตัวเอง ส่วน cost จดค่าใช้จ่ายการจัดการข้อมูลแยกต่างหาก

จำง่าย ๆ ด้วยตารางนี้

3 กฎที่ทำให้ "เครื่องอ่านได้"

บังคับน้อย แต่บังคับชัด

สเปกครอบคลุมทั้งวงจรชีวิตของ DMP แต่เริ่มต้นมีแค่หลัก ๆ ที่ต้องตอบ (ชื่อแผน, ผู้ติดต่อ, ชื่อ dataset, มีข้อมูลส่วนบุคคล/ของอ่อนไหวไหม ฯลฯ) ที่เหลือเป็น optional — หน่วยงานอย่างผู้ให้ทุนจึงบังคับเพิ่มเองได้ตาม use case ของตัวเอง โดยไม่ทำให้ระบบคนอื่นอ่านไม่ออก

คำตอบต้องเลือกจากลิสต์

หลายช่องเป็น controlled vocabulary — เช่น การเข้าถึงตอบได้แค่ open / shared / closed, ข้อมูลส่วนบุคคลตอบได้แค่ yes / no / unknown เครื่องเลยไม่มีทางตีความคำตอบผิด

ID ใช้แม่แบบเดียวกันทั้งเล่ม

dmp_id, dataset_id, contact_id, funder_id… ทุกตัวเป็นกล่องสำเร็จรูปเหมือนกัน: identifier + type — เขียนโค้ดอ่านครั้งเดียว ใช้ได้กับทุกช่อง

ตารางอ้างอิงฟิลด์ราย entity

สรุปจากตาราง Properties ใน README โดยตรง — คำอธิบาย, เงื่อนไขบังคับ, cardinality และตัวอย่าง (เลื่อนตารางได้ในแนวนอน)
