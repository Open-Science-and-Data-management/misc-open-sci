# บันทึกความต้องการระบบ (Requirement Brief)
**ระบบติดตามความคืบหน้าโครงการวิจัย — Research Progress Tracking System**
*ฉบับย่อ 1 หน้า · อัปเดต 16 กันยายน 2026*

---

## 1. ภาพรวมของระบบ

ระบบเว็บไซต์สำหรับ**นักวิจัยและคณะกรรมการ** ทำหน้าที่แปลง **Proposal (เอกสาร .docx)** ของนักวิจัยให้เป็น **DMP: แผนงานรายสัปดาห์ของทั้งโปรเจกต์** (week 1, 2, ... แต่ละสัปดาห์ต้องส่งเอกสารอะไร) — ช่วยให้นักวิจัยอัปโหลดเอกสารและติดตามงานได้ง่ายขึ้น และคณะกรรมการเห็นความก้าวหน้าได้ชัดเจนในที่เดียว

## 2. ผู้ใช้งาน (Roles)

| บทบาท | หน้าที่หลัก | AI Function |
|---|---|---|
| นักวิจัย (Researcher) | อัปโหลด proposal, สร้าง/แก้ไข DMP, อัปโหลดรายงานรายสัปดาห์ | ✅ มี (จำกัดจำนวนครั้งการ gen) |
| คณะกรรมการ (Committee) | ตรวจ DMP, approve/reject, ติดตามความคืบหน้าผ่าน progress bar | ❌ ไม่มี |
| ผู้บริหาร (Chief) | **เหมือนกรรมการทุกอย่าง** ไม่มีอำนาจพิเศษ | ❌ ไม่มี |
| ผู้ดูแลระบบ (Administrator) | แก้ไข DMP ของนักวิจัยได้โดยตรง | ❌ ไม่มี |

## 3. ขั้นตอนการทำงาน (Flows)

**นักวิจัย:** อัปโหลด proposal → เลือกให้ AI gen DMP (หรือสร้างเองแบบ manual) → แก้ไขจนพอใจ → submit → รอ approve → ได้รับแจ้งเตือนผล → ทำงานตามแผน อัปโหลดรายงานรายสัปดาห์

**คณะกรรมการ:** ตรวจ DMP → กรรมการ**ทุกคน**กด approve ถึงจะผ่าน → ระบบแจ้งเตือนนักวิจัย → ติดตามความคืบหน้าต่อเนื่อง / ใครคนใดคนหนึ่ง reject → แจ้งให้นักวิจัยแก้ไข

**ผู้ดูแลระบบ:** แก้ไข DMP ของนักวิจัยได้โดยตรง

## 4. ข้อกำหนดสำคัญ (Key Requirements)

- **DMP เป็นแผนรายสัปดาห์ของทั้งโปรเจกต์** สร้างตอนต้นและ approve ก่อนเริ่มทำงาน ไม่ใช่รายงานประจำสัปดาห์
- **AI gen เนื้อหาแบบ dynamic** ตามคำอธิบายโครงการ แต่ **form metadata ตอนอัปโหลดไฟล์เป็นแบบตายตัวชุดเดียว** ทุกเอกสารใช้ form เดียวกัน
- เอกสารที่รองรับคือ **.docx**
- **AI recheck:** เกิด**ทันทีที่นักวิจัยอัปโหลดรายงานรายสัปดาห์** — AI เช็คว่าเนื้อหา .docx สอดคล้องกับสิ่งที่แผนสัปดาห์นั้นกำหนดไหม แล้วให้ feedback ติดไปกับเอกสารเป็นข้อมูลช่วยกรรมการตัดสิน (**ไม่ block** การอัปโหลด — อัปโหลดเข้าเสมอ)
- Plan สร้างได้ทั้งจาก **AI หรือพิมพ์เองทั้งหมด** — นักวิจัยเลือกไม่ใช้ AI ก็ได้
- **ทุกครั้งที่มี plan version ใหม่ ต้องได้ approve จากกรรมการทุกคนใหม่เสมอ**
- นักวิจัยมี **limit จำนวนครั้ง** ในการ gen content ด้วย AI

### Field เบื้องต้นของ form metadata (ชุดเดียว ใช้กับทุกเอกสาร)

| Field | ประเภท | หมายเหตุ |
|---|---|---|
| ชื่อเอกสาร | text | ตั้งเองหรือดึงจากชื่อไฟล์ |
| สัปดาห์ที่ (Week no.) | select | อ้างถึง DMP |
| คำอธิบาย/หมายเหตุ | textarea | สั้น ๆ |
| ไฟล์เอกสาร | file (.docx) | บังคับ |

## 7. โครงสร้างข้อมูลเบื้องต้น (ER Diagram — draft)

ลำดับชั้น: **Project → Proposal (ไฟล์ .docx) → Plan (แผนรายสัปดาห์) → Task**

📊 [ดู ER Diagram](diagrams/er-diagram.html)

**การทำงานของ AI (Gen / Update / Recheck):**

| การทำงาน | Input | Output |
|---|---|---|
| AI gen | Proposal (.docx) | Plan + Task (เติมรายละเอียดทุก field, task = แต่ละสัปดาห์ทำอะไร) |
| AI gen/update | ข้อความที่ user พิมพ์ | แก้ไข Plan / Task |
| AI recheck | รายงานสัปดาห์ที่ user อัปโหลด (.docx) | Feedback ตรวจว่าเนื้อหาสอดคล้องกับ task ของสัปดาห์นั้น — แปะไปกับเอกสาร ไม่ block |

หลัง AI gen ทุกครั้ง **user แก้ไขเองได้** ทั้ง Plan และ Task ก่อน submit

## 8. ประโยชน์ที่คาดหวัง (Expected Outcomes)

- นักวิจัยมีแผนงานรายสัปดาห์ที่ชัดเจน รู้ว่าต้องส่งอะไรเมื่อไร ลดงานเอกสารซ้ำซ้อน
- คณะกรรมการติดตามความคืบหน้าได้แบบเรียลไทม์ผ่าน progress bar ไม่ต้องไล่อีเมล/ไฟล์กระจัดกระจาย
- ทุก plan version มีร่องรอยการอนุมัติครบถ้วน (audit trail) โปร่งใสและตรวจสอบย้อนหลังได้

## ⚠️ สมมติฐานที่ยังรอยืนยัน (Open Items)

1. **AI limit** — จำกัดกี่ครั้ง ต่ออะไร (ต่อนักวิจัย / ต่อโปรเจกต์ / ต่อสัปดาห์)? ใครตั้งค่า — fix ในระบบ หรือ Admin ปรับได้?
2. **Admin แก้ DMP** — การแก้ของ Admin นับเป็น version ใหม่ที่ต้องขอ approve ใหม่ไหม?
3. **เลยกำหนดส่ง (late upload)** — ระบบต้องมีแจ้งเตือน/สถานะสีแดงเมื่อเกิน week ที่กำหนดไหม หรือแค่แสดงผลไว้เฉย ๆ?
4. **AI ใน Use Case diagram** — AI มี use case "Update plan / Commit plan" (§6) ส่วน Admin มี "Generate plan" แต่ §2 ระบุว่า Admin ไม่มี AI — ตัวไหนถูก? และ "Commit plan" ของ AI หมายถึงอะไร (commit แทนนักวิจัย หรือแค่ trigger recheck)?
